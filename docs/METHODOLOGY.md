# Curation Methodology

## Scope

The core catalog includes work in which an AI system changes an output, model
state, scaffold, updater, or criterion using evidence generated by execution,
interaction, evaluation, self-play, optimization, or prior experience.

Supporting collections include surveys, longitudinal evaluation, failure
analysis, safety, governance, and research agendas needed to assess whether
apparent self-improvement is genuine.

## Inclusion criteria

A core L0-L4 entry must identify:

1. the object that changes;
2. the signal that drives the change;
3. whether the change persists beyond the current task;
4. what remains fixed during evaluation; and
5. the deepest demonstrated rewrite.

The list also retains explicit boundary cases when they expose a common
classification error.

## Exclusion criteria

The following are not core self-evolution by themselves:

- ordinary generation with no revision or retained update;
- static RAG, tool use, memory, or multi-agent orchestration;
- storage that is never read or does not affect later behavior;
- offline human redesign presented as agent self-improvement;
- a generated artifact that improves while the agent and its future updater
  remain unchanged;
- benchmark or position papers with no self-evolving system, unless included
  in a supporting collection.

The public repository is manuscript-scoped. A record is retained only when the
compiled manuscript actively cites its BibTeX key. Supporting surveys,
benchmarks, position papers, and governance work can therefore remain when the
manuscript uses them, even though they are not core L0-L4 systems. Catalog-only
papers are not retained.

## Source reconciliation

Each release reconciles active TeX citations with the manuscript BibTeX
library. The active citation set is authoritative for repository membership:
`data/papers.json` must contain exactly one canonical record for each active
BibTeX key and no additional paper. Historical detailed-catalog metadata can
supply classification rationale and artifact evidence for those retained
records, while BibTeX supplies bibliographic metadata and embedded links.

The importer strips TeX comments before extracting citations. This prevents
superseded, commented-out prose from silently re-entering the public list.

A work's level follows the deepest demonstrated rewrite recorded by the curated
catalog, so a citation in a deeper chapter's discussion never promotes it. Its
subcategory, however, follows the subsection the manuscript currently cites it
in, so the rendered list tracks the chapter structure as the manuscript is
revised.

Each level chapter opens by defining its evolution target, and that opening
prose cites much of the work the chapter later discusses in detail. The topical
subsection is the more informative placement, so a work is filed under a
chapter's definition heading only when the chapter cites it nowhere else.

Historical source headings are crosswalked onto the current taxonomy during
import rather than re-curated entry by entry. They share the manuscript's L0-L4
numbering, so only the subsection structure needs the crosswalk.

The importer reads each level's number from the chapter heading that declares it
and stops when that disagrees with `data/taxonomy.json`. See the numbering
history in `docs/TAXONOMY.md`.

## Deduplication

Canonical identity uses the first available identifier in this order:

1. arXiv identifier;
2. DOI;
3. OpenReview forum identifier;
4. stable proceedings URL;
5. normalized-title hash as a temporary fallback.

Display names and BibTeX keys are never used as global identifiers. One work is
stored once and can have multiple section memberships. Fuzzy title similarity
produces a review warning; it never triggers an automatic merge.

A proceedings URL whose path is itself a minted DOI resolves at rung 2 rather
than rung 4, so an ACL Anthology or Nature record shares an identifier space
with the same venue's `doi.org` citations instead of splitting across two
schemes.

A manuscript that moves from citing a preprint to citing the published record
retires the identifier under which a work was curated. The curated entry keeps
its identifier and declares the published one in `identity_aliases`, so both
citations resolve to a single record. `possible_duplicate_reviews` in the import
report lists the unmatched curated entries whose titles resemble a newly
synthesized entry, which is where an undeclared alias shows up.

Researched link records are keyed by the identifier a work carried when its
links were collected. When that identifier is retired, a record is retargeted by
an exact normalized-title match; an ambiguous title is left unmatched.

A bibliography can hold several keys for the same work. Every such key is
recorded against the single canonical record, and the manuscript's own choice of
key wins when the keys disagree on metadata. Because the normalized-title hash
is itself the last rung of the ladder, an exact normalized-title match merges
into an already-identified work; a title fragment too short to identify a work
on its own is never used as a match key.

## Link policy

Every work must have a canonical paper link. Code and project links are added
only when supported by at least one of:

- the paper itself;
- an official project page;
- an official repository identifying the paper;
- a referenced curated list with an unambiguous paper identifier.

Third-party reproductions must be labeled as such. An announced code URL that
currently returns 404 remains in the machine-readable audit for provenance but
is omitted from the rendered paper list. A missing code link means “no
source-backed public implementation found,” not “no implementation exists.”

## Verification states

- `source_listed`: present in a source but not yet live-checked.
- `verified`: returned a successful HTTP response.
- `redirected`: resolved successfully through a redirect.
- `rate_limited`: the host refused a high-rate check.
- `blocked`: access requires authorization or rejects automated requests.
- `invalid`: returned a persistent not-found response.
- `unreachable`: failed because of a network or server error.

The audit date and HTTP result are stored per artifact. Link checks never
silently replace an official URL with a similarly named repository.

## Updating the catalog

1. Import or edit a canonical work record.
2. Provide a rewrite-object rationale and source evidence.
3. Collect artifact links the papers announce themselves.
4. Validate identifiers, taxonomy, and exact manuscript membership.
5. Run the link audit.
6. Regenerate README and audit reports.

For step 3, use author-stated artifact links from the paper, abstract, project
page, or official repository. Curated records should preserve existing
artifacts and explicit negative evidence unless stronger source evidence is
available.

All generated paper lists derive from `data/papers.json`; hand-editing generated
README entries is not supported.
